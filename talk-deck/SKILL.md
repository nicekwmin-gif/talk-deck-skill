# 발표 덱 만들기

결론이 이미 나온 내용을 **청중이 기억하고 움직이게 포장**하는 작업이다. 새 분석이 아니다.

좋은 덱은 프롬프트 한 번으로 나오지 않는다. 이 스킬의 품질은 세 가지에서 나온다.
① 만들기 전에 이야기를 글로 확정한다. ② 만든 슬라이드를 **이미지로 렌더해서 직접 본다**. ③ 사용자와 수정 라운드를 여러 번 돈다.
세 가지 중 하나라도 건너뛰면 "AI가 만든 슬라이드"가 된다.

## 처음 쓸 때: 환경 준비 (사용자에게 시키지 않고 직접 한다)

```
python <skill>/scripts/check_env.py --install
```

- 빠진 Python 패키지(`python-pptx`, `Pillow`, `matplotlib`)는 이 명령이 설치한다.
- 렌더러(PowerPoint 또는 LibreOffice + pdftoppm)가 없으면 스크립트가 설치 명령을 알려 준다. 시스템 프로그램이므로 **사용자에게 물은 뒤** 설치한다.
- 웹 검색 도구를 쓸 수 없으면 사용자에게 켜 달라고 한 번 요청한다. 안 되면 D절의 대체 방법(자료 목록을 넘김)으로 간다.
- 이 스킬은 다른 스킬 없이 혼자 돈다. pptx·이미지·검색용 스킬이나 도구가 이미 있으면 써도 되지만 이 문서의 순서와 규칙이 우선이다.
- 한 프로젝트에서 한 번 확인했으면 다시 돌리지 않는다.

## 0. 먼저 확인할 것

이미 들은 것은 다시 묻지 않는다. 한 번에 모아서 묻는다.

| 항목 | 왜 필요한가 | 답이 없을 때 기본값 |
|---|---|---|
| 발표 종류 | 흐름이 달라진다 (1절) | 자료를 보고 추정해서 확인받는다 |
| 행사·날짜·발표 시간 | 장 수와 장당 시간 | 15분 = 11–14장, 20분 = 16–20장 |
| 청중 (누가 듣나, 무엇을 결정하나, 전문성) | 용어 수위, 예상 질문, 주장 강도 | 반드시 묻는다. 기본값 없음 |
| 청중이 발표 뒤에 하길 바라는 행동 | 마지막 장과 한 줄 메시지 | 반드시 묻는다 |
| 슬라이드 언어 / 노트(대본) 언어 | | 슬라이드와 노트 모두 발표 언어 |
| 사용자가 이미 쓴 기획안·순서 | 사용자의 흐름이 우선 | 없으면 1절의 기본 흐름 |
| 원자료 위치 (데이터, 그림, 사진, 이전 덱, 로고, 회사 템플릿) | | 작업 폴더를 먼저 훑는다 |
| 대외 공개 가능 범위 (미공개 수치, 고객사 이름, 가격) | 기업용 덱에서 사고가 나는 곳 | 불확실하면 넣지 않고 묻는다 |

장마다 **몇 초 말할지**를 기획 단계에서 정한다. 20초짜리 장에 표 세 개를 넣지 않기 위해서다.

## 1. 발표 종류별 기본 흐름

| 종류 | 청중이 알고 싶은 것 | 기본 흐름 |
|---|---|---|
| 기업 대상 데이터·제품 설명 | 우리 문제가 풀리나, 근거가 있나, 다음에 뭘 하면 되나 | 청중의 문제 → 지금 방식의 한계 → 우리가 가진 것(한 문장) → 근거 데이터 2–4장(한 장에 주장 하나) → 적용 예시·조건 → 한계와 아직 모르는 것 → 다음 단계(구체적 요청) |
| 행사·대중 발표 | 왜 들어야 하나, 무엇이 새롭나 | 질문 하나를 연다 → 배경(왜 중요한가) → 우리 이야기 → 결과 2–3장 → 의미 → 처음 질문으로 닫는다 |
| 학회·세미나 연구 발표 | 무엇을 물었고 무엇을 찾았나 | 환경·현상 → 대상 → 공백(gap) → 목적 → 방법(짧게) → 발견(한 장에 하나) → 결론 → 진행 중 연구 |

기업용 덱에서 지킬 것:
- **청중의 문제로 시작한다.** 회사 소개·연혁으로 시작하지 않는다. 필요하면 맨 뒤 백업으로 보낸다.
- 데이터 한 장마다 "그래서 당신에게 무엇이 달라지나"를 헤드라인이나 노트 첫 문장에 넣는다.
- 한계를 숨기지 않는다. 시험 조건, 표본 수, 아직 확인 안 된 것을 한 장 또는 캡션으로 먼저 말한다. 실무 담당자가 반드시 묻는다.
- 마지막 장은 "감사합니다"가 아니라 **요청 한 가지**(시험 적용, 샘플 제공, 다음 미팅)와 연락처다.
- 가격·계약 조건·경쟁사 비교는 사용자가 넣으라고 한 것만 넣는다.

세부 방법은 `references/storyline_and_review.md`에 있다.

## 2. 원칙

- **포장이지 재분석이 아니다.** 받은 수치를 인용만 한다. 새 통계를 돌리거나 수치를 다시 계산하지 않는다. 자료 안의 명백한 불일치(그림과 본문 수치 차이)는 한 줄로 알린다.
- **원본은 건드리지 않는다.** 받은 pptx·그림·데이터는 `assets/`나 `input_from_user/`에 사본을 떠서 쓴다. 지울 것은 `_old/`로 옮기고 README에 한 줄 남긴다.
- **확인 안 된 사실은 쓰지 않는다.** 수치·인용·"최초/유일/업계 최고" 같은 말은 자료에서 확인한 것만 쓴다. 문헌은 초록이나 본문을 직접 열어 확인한다. 확인 못 한 것은 `[확인]`으로 표시해 사용자에게 넘긴다.
- **출처는 슬라이드 하단에 적는다.** 그림·사진·데이터·인용 모두.
- **데이터를 꾸미지 않는다.** 그림이 이야기와 맞지 않으면 데이터를 바꾸지 말고, 말로 처리하거나 그 장을 빼자고 제안한다. 축을 잘라 차이를 키우지 않는다.
- **계획을 실적처럼 쓰지 않는다.** 예정·검토 중·가능성은 그렇게 적는다.

## 3. 작업 순서

각 단계 끝에서 사용자 확인을 받는다. 확인 없이 다음 단계로 넘어가지 않는다(특히 A→C).

### A. 스토리라인 (첫 산출물, 슬라이드보다 먼저)

`output/<talk>_storyline_vN.N_YYYYMMDD.md`에 쓴다.

1. **한 줄 메시지**: 청중이 하나만 기억한다면 무엇인가. 한 문장.
2. **이야기의 실**: 처음에 열고 마지막에 닫는 질문이나 대비 하나.
3. **슬라이드 표**: # · 헤드라인(결론 문장) · 청중이 가져갈 한 줄 · 쓰는 자료(파일 경로) · 초
4. 초 합계. 실제 발표는 적은 시간보다 20–30% 길어지므로 발표 시간의 75–80%로 맞춘다.
5. 확인이 필요한 것 목록.

헤드라인만 순서대로 읽어도 이야기가 통해야 한다. 통하지 않으면 슬라이드를 만들지 않고 스토리라인을 고친다.

### B. 사실 확인표

슬라이드에 올라갈 수치·인용·고유명사를 표로 모은다: 주장 · 정확한 수치 · 출처(파일·쪽·URL) · 어떻게 확인했나(원자료 / 본문 / 초록 / 보도자료뿐). `_tmp/factsheet.md`에 둔다. 표에 없는 수치는 슬라이드에 쓰지 않는다.

### C. 3관점 검토 (스토리라인 단계에서 한 번, 첫 렌더 뒤 한 번)

세 관점으로 따로 검토하고 결과를 표로 낸다. 하위 에이전트를 쓸 수 있으면 관점마다 하나씩 독립적으로 돌리고, 없으면 관점을 하나씩 순서대로 쓴다. **검토 중에는 파일을 고치지 않는다.**

| 관점 | 보는 것 |
|---|---|
| 가장 깐깐한 청중 | 기업용이면 의사결정자(그래서 우리에게 뭐가 좋은가, 비용·위험)와 실무 기술 담당자(조건, 표본 수, 재현성, 비교 기준). 연구 발표면 그 분야 심사위원. 근거보다 앞서 나간 문장을 찾는다 |
| 발표 코치 | 흐름이 끊기는 곳, 같은 정보 반복, 장별 전환 문장, 시간 합계, 처음과 끝의 호응 |
| 디자이너 | `references/design_system.md`의 "AI 슬라이드 증상" 11가지, 장당 단어 수, 글자 크기·색 가짓수 |

의견이 갈린 곳은 **판단 기록 표**(쟁점 · 결정 · 이유)로 남기고 사용자가 정하게 한다. 형식은 `references/storyline_and_review.md`.

### D. 자료 모으기

**사용자만 가진 것은 처음에 한 번에 요구하고, 그 밖의 것은 에이전트가 찾아온다.** 무엇을 요구하고 무엇을 직접 수집하는지, 사진 라이선스 확인법은 `references/collecting_materials.md`에 있다. 0절의 질문과 함께 요구 목록을 보낸다.

| 누가 | 무엇 |
|---|---|
| 사용자에게 요구 | 핵심 데이터(원자료), 제품·연구의 정확한 설명, 청중 정보, 자기 사진, 로고·템플릿, 공개 금지 범위 |
| 에이전트가 수집 | 배경 사실·통계, 선행·비교 수치, 공개 사진·도해, 작업 폴더의 이전 덱 속 그림, 원자료로 다시 그린 그래프 |

- 수집한 사실은 B의 사실 확인표에, 사진은 후보 시트로 보여 주고 사용자가 고른 것만 쓴다.
- 웹 검색을 쓸 수 없는 환경이면 필요한 자료 목록을 사용자에게 넘기고 그 자리는 `[확인]`으로 비워 둔다.
- 쓸 그림·사진·데이터는 프로젝트 `assets/`로 **복사**하고 `assets/SOURCES.md`에 출처와 라이선스를 적는다.
- 이전 pptx에서 그림을 꺼낼 때는 pptx(zip)의 `ppt/media/`에서 뽑는다.
- 그래프는 논문·보고서용 그림을 그대로 붙이지 않는다. 슬라이드용으로 다시 그린다(matplotlib 또는 PowerPoint 기본 차트). 글자를 키우고, 그림 안 제목을 빼고, 말할 계열만 색을 준다.
- 수치 몇 개로 끝나는 것은 PowerPoint 기본 차트(python-pptx chart)나 도형으로 그린다. 자동 차트 제목은 끈다(`has_title = False`).

### E. 빌드

빌더 스크립트 하나가 덱 전체를 만든다: 프로젝트의 `scripts/build_deck.py`.

```python
import os, sys
sys.path.insert(0, r'<이 SKILL.md가 있는 폴더>/scripts')
import pptx_kit as K

K.THEME.update(font='Segoe UI', accent='3F7D2A')      # 덱 전체 글꼴과 강조색 한 개
prs = K.new_deck()                                    # 16:9, 13.333 x 7.5 in
s = K.content_slide(prs, '', 'Headline as a full sentence', source='Data: ... · Photo: ...')
K.figure(s, 'assets/fig1.png', 0.8, 2.2, 6.5, 4.4)
K.notes(prs, s, '이 장의 대본 ...')
K.renumber(prs)
prs.save(os.environ.get('DECK_OUT') or 'output/Talk_v0.1_YYYYMMDD.pptx')
```

- `pptx_kit.py` 헬퍼: `rect`, `text`(run 단위 bold·italic·위첨자·아래첨자), `bullets`(진짜 글머리표), `figure`(비율 유지), `photo`(가운데 자르기), `cover_photo`(가장자리까지 채우고 글자 쪽에만 그라데이션), `arrow`, `content_slide`, `blank_slide`, `renumber`, `notes`, `note_replace`, `click_fade`(클릭 등장), `keep_slides`, 기존 덱 편집용 `title_of`, `slide_by_title`, `find`, `set_text_keep_style`, `move`, `remove`.
- 회사 템플릿(pptx/potx)이 있으면 `Presentation(<템플릿 사본>)`으로 열어 그 레이아웃·글꼴·색을 따른다. 템플릿이 없으면 `references/design_system.md`의 기본 체계를 쓴다.
- 확인용 빌드는 환경변수 `DECK_OUT`으로 임시 폴더에 내보낸다. `output/`에는 사용자가 볼 버전만 둔다.
- 필요한 패키지: `python-pptx`, `Pillow`. 없으면 `pip install python-pptx pillow`.

### F. 렌더하고 눈으로 본다 (건너뛰지 않는다)

스크립트가 에러 없이 끝난 것과 슬라이드가 쓸 만한 것은 다르다. **모든 빌드 뒤에 PNG로 렌더해서 이미지를 직접 열어 본다.**

Windows + PowerPoint:
```
powershell -File <skill>/scripts/render_pptx.ps1 -Pptx deck.pptx -OutDir <tmp>/png [-Slides "8,13"]
python <skill>/scripts/overview_grid.py <tmp>/png <tmp>/overview.jpg
```
PowerPoint가 없으면(Mac·Linux) LibreOffice:
```
soffice --headless --convert-to pdf --outdir <tmp> deck.pptx
pdftoppm -png -r 120 <tmp>/deck.pdf <tmp>/png/slide      # 이름을 slide-01.png 형식으로 맞춘다
```
LibreOffice는 글꼴·줄바꿈이 조금 다르게 나온다. 최종 확인은 사용자가 PowerPoint에서 한다고 알린다.

- `render_pptx.ps1`은 사본을 창 없이 읽기 전용으로 열고 `Close()`만 한다. **PowerPoint를 `Quit()` 하지 않는다**(사용자가 열어 둔 다른 문서까지 닫힌다).
- 렌더가 아예 불가능한 환경이면 그 사실을 사용자에게 알리고, 사용자가 화면 캡처를 주면 그것을 보고 고친다. 보지 않고 "완성"이라고 하지 않는다.
- 볼 것: 글자 겹침·잘림, 상자 밖으로 넘친 글, 출처 줄과의 충돌, 슬라이드 밖으로 나간 도형, 그림 찌그러짐, 자동 차트 제목, 차이를 과장하는 축, 그림 속 숫자와 슬라이드 숫자 불일치, 한 장에 메시지가 둘인 곳.
- 전체 흐름은 overview 그리드 한 장으로 보고, 고친 장은 원본 크기 PNG로 본다.

### G. 수정 라운드

- 지적 하나마다 빌더(또는 수정 스크립트)만 고치고 → 해당 장만 렌더해 확인하고 → 무엇을 바꿨는지 짧게 알린다.
- 디자인을 크게 바꿀 때는 시안 2–3개를 PNG로 만들어 보여 주고 사용자가 고르게 한다. 색도 마찬가지다.
- 큰 방향 변경 전에는 빌더 사본을 `scripts/_old/`에 둔다.

**사용자가 손으로 고친 pptx를 다시 주면 그 파일이 새 기준이다.** 빌더로 다시 만들면 사용자의 수정이 사라진다.
1. 사본을 `input_from_user/<name>_user.pptx`로 둔다.
2. 수정 스크립트(`scripts/revise_deck_vN.py`)가 사본을 열어 **제목과 shape 이름으로 찾아** 고친다(`K.slide_by_title`, `K.find`). 슬라이드 번호나 좌표로 찾지 않는다.
3. 노트 문구는 `K.note_replace(s, old, new)`로 고친다. 찾는 문구가 없으면 멈추므로 조용히 빠지지 않는다.

### H. 최종 검토와 최종본

1. `references/final_review_checklist.md`를 따라 슬라이드와 노트를 한 번에 훑는다. 지적은 목록으로 모아 한 번에 반영하고, 반영 결과를 표(위치 · 수정 · 이유)로 보고한다.
2. `output/<Talk>_vN.N_YYYYMMDD.pptx`로 저장한다. 파일명에 `final`을 쓰지 않는다.
3. 전체를 다시 렌더해 모든 장을 본다.
4. 보고: 파일 경로, 고친 것 표, 남은 `[확인]`, 발표 PC에서 직접 확인할 것(클릭 애니메이션, 글꼴, 동영상).
5. `output/README.md`에 버전마다 한 줄(무엇이 바뀌었나, 어느 스크립트로 만들었나)을 남긴다.

## 4. 디자인 요약

전체 규칙과 슬라이드 틀은 `references/design_system.md`에 있다. 빌드 전에 읽는다. 핵심만 적으면:

- 헤드라인은 주어와 동사가 있는 **결론 문장**이다. "분석 결과"가 아니라 "처리 후 불량률이 절반으로 줄었다".
- **한 장에 메시지 하나, 40단어 이하**(출처·축 눈금 제외). 남는 공간은 채우지 않고 비운다.
- 글자 크기는 4단계만, 강조색은 한 개만. 색에는 뜻 하나만 준다(예: 강조색 = 우리 제품·우리 데이터).
- 카드 격자, 알약 라벨, 번호·아이콘 원, 대문자 소제목, 하단 요약 띠, 이모지를 쓰지 않는다.
- 화면에서 뺀 내용은 버리지 않고 **노트(대본)나 백업 슬라이드**로 옮긴다.
